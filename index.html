fallcore-mcp

Your own model, as tools an AI agent can call. Add it to Claude Code, Cursor, Cline or Windsurf. The agent gets eight tools that talk to your model, either through a FallCore proxy (local model first, a frontier model only when the proxy falls through, every call in the proxy's log) or straight to plain Ollama. It is free and MIT-licensed, and it is tested end to end.

Start here

  1. Have a model running. Plain Ollama is enough to start (for example ollama pull llama3.2:1b). For the log, the cost counts and local-first routing, run a FallCore proxy in front of it.
  2. Add the server to your agent. In Claude Code:
    claude mcp add fallcore -s user --transport stdio -- npx -y github:sjgant80-hub/fallcore-mcp
    It installs from GitHub; it is not on npm.
  3. Tell it where your model is, if it is not plain Ollama on this machine, and which model to use:
    FALLCORE_ENDPOINT=http://localhost:11434
FALLCORE_MODEL=llama3.2:1b
  4. Ask your agent to use the fallcore tools: "list the models", "ask the local model …".

How it works

  1. Your agent calls a tool, for example chat with a prompt.
  2. fallcore-mcp turns it into an HTTP request to FALLCORE_ENDPOINT. For chat, that is an Anthropic-style POST /v1/messages.
  3. A FallCore proxy answers on the local model first, falls through to a frontier model only when it must, and writes the call to its log. Plain Ollama answers the same request itself.
  4. The answer comes back to the agent as the tool's result: the text, plus which tier answered and what it cost, when the proxy says.
  5. If the endpoint does not serve a tool, the agent gets an error result that says why. For example: "health needs the FallCore proxy; plain Ollama does not serve it".

Adoption: rolling it out in a team

  1. Start on one laptop with plain Ollama. chat and models work at once. It shows whether your agents can do useful work on a local model at all.
  2. Put a FallCore proxy in front when you want the record. Every agent call is logged, routed local first, and counted (stats).
  3. Point everyone's agent at the one proxy (FALLCORE_ENDPOINT, on your network). The model, the log and the routing rules then live in one place you control.
  4. Review the log (recent_logs, admin key) to see what agents ask your model, and what fell through to a frontier model.

For business: the straight answers

What it costs. The software is MIT: no licence fee. You pay for the machine your model runs on, and for any frontier calls the proxy falls through to, at your provider's own rates. This page computes no saving: that depends on your traffic, and the proxy's stats tool counts it from your own calls.
Where your data goes. chat, models, health, stats and recent_logs go only to the endpoint you set. With a local endpoint, that is your own machine or network. The three factory tools call the hosted FallCore Factory at fallcore-factory.onrender.com; leave them unused if nothing may leave. A frontier fallthrough, when the proxy makes one, sends that prompt to the provider whose key you gave it.
Security. It runs as a local process your agent starts, and listens on no port. Its one direct dependency is the official MCP SDK (which brings its own). Keys come from environment variables. It never writes them anywhere. An endpoint with a user and password in its URL is refused (Node's fetch will not send one), and the refusal never shows the password. Protect a remote proxy at the network or with the proxy's own keys. The code is under 200 lines; read it before you run it.
Compliance. It does not make any use compliant. What it gives you is a single place, the proxy's log, where agent calls to your model are recorded. Whether that meets your obligations is yours to judge.
Support and ownership. Supplied by AI Native Solutions. Start through that site. Support, any service levels, warranty and liability are agreed per deployment, in that deployment's agreement. The software keeps working without us: it is MIT, and the source is yours to keep.
Risks, answered straight.
  • The answer quality is the model's. A small local model answers worse than a frontier one. Try it on your own work first. The run above used a 1B model, and its answer shows it.
  • The factory is hosted on a free tier. It can be slow to wake, or down. Nothing else depends on it.
  • Plain Ollama keeps no log of agent calls. The record needs the FallCore proxy.

Questions buyers asked

A CTO and a bank compliance officer read this page cold (a local model played each) and listed what it left open. The answers:

Is the traffic encrypted?

fallcore-mcp adds no encryption of its own: it speaks to the endpoint you give it, over HTTP or HTTPS as that URL says. Over the network, give it an https:// endpoint, or keep the proxy inside your network. The link between your agent and fallcore-mcp is a local pipe (stdio) between two processes on one machine.

What does it store?

Nothing. It writes no file and keeps no state between calls. The FallCore proxy keeps the log, when you use it, under its own retention settings.

What does it need to run?

Node.js 20 or later, on the machine where your agent runs. Your model's hardware needs are your model's (see Ollama or the FallCore proxy). Its only direct dependency is the official MCP SDK.

How do we pin a version and update it?

Install from a tag, not from the latest commit: npx -y github:sjgant80-hub/fallcore-mcp#v0.2.0. You update by changing the tag, after reading what changed. The tests and the witness gate run in CI on every commit.

What happens when something fails?

Every failure comes back to the agent as an error result with the reason, never a crash. That covers an endpoint that is down, a 404 for a tool the endpoint does not serve, a missing prompt and an unknown tool. A call to your endpoint gives up after 60 seconds, a factory call after 90.

GDPR, the FCA, our own policies?

fallcore-mcp decides nothing about your data: it passes each prompt to the endpoint you configured and returns the answer. Which personal data reaches the model, where that model runs, and what the proxy logs are your deployment's choices. Assess them as you would any internal system. A local endpoint keeps prompts on your own machines; a frontier fallthrough does not, so set the proxy's routing to match your policy.

Does it scale to many agents?

Each agent starts its own copy. It holds no state, so copies do not interfere. How many calls you can serve is your endpoint's capacity, not this server's.

Why this exists

An AI agent that can call tools will call someone's model, and most agents default to a rented one. An MCP server is the agent's own way of reaching a tool, so putting your own model behind one makes it the easy path. Behind a FallCore proxy that model answers locally first and keeps a log of what agents asked it. The server itself does no thinking and keeps nothing: it is a thin, tested translation between the agent's tool calls and your endpoint's HTTP.

It completes a layering, from the operating system up to the agent: an OS call, a command, a command line, an API in front of it, and the MCP that lets an AI agent call the API. The layering is Thomas Frumkin's.
